## PR #1：跨平台技能读取与实体安装过滤

### 背景与意图

作者报告 Windows 上默认文本编码造成 `UnicodeDecodeError`，以及硬链接 `.git/objects/pack` 时出现权限错误。用户需要正常安装、查看含非 ASCII 内容的技能，而不必调整系统 locale 或仓库内部权限。[原始报告与实现](https://github.com/reorx/skm/pull/1/files)

### 独立需求描述

技能管理器应以 UTF-8 读取 `SKILL.md`，使技能发现与内置分页查看行为不依赖操作系统默认编码。创建实体安装目录时，应排除不属于技能运行内容的仓库元数据，避免为安装技能复制 Git 内部状态。

验收应覆盖：中文或特殊符号出现在技能正文时，发现和查看均成功；源目录含 `.git` 时，实体安装不包含该目录；常规脚本和资源仍完整安装。

### 实现范围与价值判断

PR 修改 `detect.py` 与 `commands/view.py` 的 `read_text`，显式指定 UTF-8；同时在硬链接遍历中跳过所有点号开头条目和软链接。改动很小，却解决核心流程阻断，值得保留。

需要区分“排除 `.git`”与“排除所有隐藏资源”：后者是实际实现的更宽泛规则。如果某个技能依赖隐藏文件或符号链接资源，实体安装可能不完整。该规则现在仍在 `linker.py` 中；本次没有发现具体受影响技能，因此作为边界记录，不认定为已发生故障。该 PR 也没有提供完整 Windows 平台支持的证明，不能据此宣称全部命令已通过 Windows 验收。

## PR #2：安装路径跟随 agent 配置目录

### 背景与意图

原先 agent 目录写死在源码中。用户通过环境变量改变 agent 配置根目录后，SKM 仍将技能安装到旧位置，造成两套目录不一致。[PR 正文](https://github.com/reorx/skm/pull/2)

### 独立需求描述

用户已经为 agent 指定配置根目录时，SKM 应将技能安装到该根目录下的 `skills` 子目录；未设置或设置为空时使用默认目录。这个解析结果应贯穿安装、更新和列表展示。

此 PR 的具体映射是 `CLAUDE_CONFIG_DIR` 对应 Claude，`CODEX_HOME` 对应 Codex。这里描述的是 PR 和 SKM 当前实现，不额外推断这些产品所有版本的配置约定。

验收应覆盖：默认目录不变；设置覆盖值后安装进入新目录；`~` 正确展开；lock 仍使用既有路径压缩规则；后续列表能识别安装目标。

### 实现范围与价值判断

`types.py` 增加 `_get_known_agents()`，应用两个环境变量覆盖。需求直接避免“装好了却不能用”，价值高，且无需用户维护两套重复配置。

当前 `KNOWN_AGENTS` 在模块导入时计算，普通 CLI 进程通常足够，但同一进程内改变环境后不会自动重新解析。#7 改为命令执行过程中的统一解析，更容易保证一致性。后续若同时支持配置文件覆盖，需要明确优先级，而非在各命令中分别处理。

## PR #3：列表中的 agent 归属正确且稳定

### 背景与意图

这是 #2 带出的配套问题：环境变量解析得到绝对目录，lock 使用 `~` 压缩路径；两种表示直接比较时不匹配。作者说“list 不显示安装的技能”，但从实现看，具体修复的是技能条目中的 agent 归属显示，技能条目本身仍从 lock 读取。[变更与测试](https://github.com/reorx/skm/pull/3/files)

### 独立需求描述

同一安装路径无论使用绝对形式还是 `~` 形式，列表均应显示正确的 agent 名称。路径展示的隐私压缩不应影响路径身份判断。

验收应覆盖：默认目录、环境变量覆盖目录、lock 中的缩写路径都能识别；不同目录即使名称前缀相同，也不能认作同一 agent。

### 实现范围与价值判断

PR 在比较前也展开 lock 路径，并增加安装与列表测试。它保障“安装事实”和“用户看到的状态”一致，值得保留。

但当前比较仍使用字符串 `startswith`：例如 `~/.agents/skills-extra/demo` 会被 `~/.agents/skills` 匹配，误显示为 `standard`。这是代码可直接确认的边界缺陷；#7 已提出使用安装路径父目录精确比较，并有对应测试。建议将此修复视为独立的正确性需求，优先于大型配置重构。

## PR #6：跨文件系统的实体安装与刷新

### 背景与意图

[Issue #4](https://github.com/reorx/skm/issues/4) 给出实际使用场景：store 所在的 `~/.local/share` 与 home 位于不同 Btrfs 子卷，硬链接失败。作者同时提出两个方向：增加 reflink 回退，或允许用户覆盖安装策略。#6 处理前者，#7 延续后者。

### 独立需求描述

对于需要真实目录的 agent，用户应能在硬链接不可用的存储布局中安装技能。系统应自动选取可用方式，必要时普通复制，不能因为一种优化不适用就阻断安装。更新后，agent 使用的实体内容应反映新版本；无法完成的真实 I/O 故障必须暴露。

验收应覆盖：同设备硬链接；跨设备时尝试 reflink；不支持 reflink 时复制；权限、磁盘故障不得误作“不支持”吞掉；更新后检查目标文件内容及删除行为，而不只检查 lock commit。

### 实现范围与价值判断

PR 引入 `clonefile.py`：Linux 使用 FICLONE，macOS 使用 `clonefile(2)`；`linker.py` 根据设备和能力选择硬链接、reflink 或复制；`update` 传入 `force=True` 以允许重建旧实体目录。[PR 实现](https://github.com/reorx/skm/pull/6/files)；[维护者补充 macOS 支持的说明](https://github.com/reorx/skm/pull/6#issuecomment-4087075634)。

需求价值高，但应准确说明保证：跨设备并不保证 reflink 可用，普通复制才是最终兼容回退；硬链接与 reflink 也不是相同隔离模型，硬链接原地编辑会影响共享 inode 的另一端，不能描述为独立副本。

刷新也有两个层次：当前 `_materialize_tree` 跳过已存在文件；但外层 `link_skill` 在发现目标与源不一致、且 `force=True` 时会删除目录重建。因此不能仅凭内层函数断言“当前所有 update 都不会更新内容”。#7 的刷新改动应结合外层分支与端到端内容断言评估。

## PR #7：统一 agent 配置与用户覆盖

### 背景与讨论演变

[Issue #5](https://github.com/reorx/skm/issues/5) 最初希望把 `KNOWN_AGENTS`、环境变量映射、`AGENT_OPTIONS` 合并到静态配置。维护者随后明确建议复用 `skills.yaml` 的 `agents`，增加 `agents.override`，避免让用户管理第二份配置文件。[维护者意见](https://github.com/reorx/skm/pull/7#issuecomment-4087118375)

最新实现已经采用该意见：内置定义保留为 Python 中的 `DEFAULT_AGENT_SPECS`，用户覆盖写在 `skills.yaml`。因此旧标题“move agent specs to bundled config file”已不准确；也不能因为 issue #5 已关闭，就判断需求已经合入。

### 独立需求描述

用户应能在现有配置文件中为内置 agent 指定技能目录与安装方式，无需修改 SKM 源码。安装、更新、列表必须使用同一套解析结果，同时保持现有配置兼容。

```yaml
agents:
  default:
    - claude
    - standard
  override:
    claude:
      path: ~/.agents/skills
      install_mode: materialize
```

这里 `path` 是完整技能目录，环境变量值则是配置根目录，二者含义不能混淆。`materialize` 表示生成实体目录，具体采用硬链接、reflink 还是复制由系统决定。

最新实现的路径优先级为：`--agents-dir` > `agents.override.<name>.path` > agent 环境变量 > 内置路径。只覆盖 `install_mode` 不会取消环境变量路径。`agents.default` 限定部署范围，包级 includes/excludes 再过滤该范围。

验收应覆盖以下行为：

- 旧配置继续使用现有默认目录与模式；未知 agent 或非法模式明确报错。
- 路径覆盖、模式覆盖可以单独设置；优先级在安装、更新和列表中一致。
- 直接安装的交互选项只包含默认启用的 agent。
- `list` 能识别自定义安装位置；配置损坏时仍可带警告读取 lock。
- 切换模式、迁移路径后，lock 与实际安装保持一致，不误删未管理内容。

### 价值与取舍

建议接受统一配置的产品方向。它直接回应 #4 中“让我选择安装方式”的诉求，也能让不需要实体目录的用户自行选择软链接，避免为某一 agent 的兼容问题要求所有用户接受同样策略。最新实现仅支持覆盖内置 agent，不支持注册任意新 agent；不宜将其宣传为通用插件注册机制。

合入前最需要确认的是**实体更新遇到目标多余文件时如何处理**。当前主分支的测试要求上游删除的文件从实体安装中消失；#7 将该测试改成“旧文件保留，输出警告”。当目录其余内容仍被判断为受管理副本时，会走保留分支；不匹配且 force 重建时仍可能删除，因此并非所有情况下都保证保留。

保留有助于避免误删用户添加的文件，但也可能让过期说明或脚本继续影响 agent；这改变了声明式同步的预期，不能当作内部重构附带接受。建议单独决定同步契约，并补充“只删除”“修改加删除”“用户添加文件”三类验收。更完整的后续方案是保存受管理文件清单或内容指纹，让删除判断基于所有权；这是本次建议，不是 PR 已提供的能力。

维护者曾在 [早期 review](https://github.com/reorx/skm/pull/7#issuecomment-4242977222) 指出刷新跳过现有文件；最新 head 已改为替换现有文件，并强化更新后内容断言，不能把旧 review 原样当作未修复结论。作者的[最新回复](https://github.com/reorx/skm/pull/7#issuecomment-5548017604)报告 140 个非网络测试通过；这是作者报告，本次未执行 PR 分支测试，也未进行跨平台实机验收。
